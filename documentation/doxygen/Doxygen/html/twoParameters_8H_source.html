41 Description
42  Regime map model that depends on two parameters.
43 
44  Dictionary example
45  \verbatim
46  regimeMaps
47  {
48  "mapName"
49  {
50  type twoParameters;
51 
52  // These correspond to the desired parameters for the 2-D map.
53  // These can only correspond to the IOobject names of
54  // tvolScalarField ype objects in the mesh object registry. No
55  // other volTypeFields are supported
56  parameter1 "name1";
57  parameter2 "name2";
58 
59  // This sets the size (width) of the interpolation region that
60  // sits across the line that separates two different regimes. This
61  // is used to avoid sharp changes in the transfer coefficients that
62  // might depend on this flow regime map to avoid numerical
63  // instabilities. In order to deal with the fact that the two axes
64  // (or dimensions) of the regime map might refer to parameters with
65  // wildy different domains (e.g. one axis corresponds to a volume
66  // fraction, which spans 0-1, while the other corresponds to a
67  // mass flux, which can spans up to e.g. 10000 kg/m2/s), it is
68  // difficult to define an absolute meaningful "distance" in this
69  // 2-D domain. Thus, this width refers to the relative width of
70  // this interpolation region compared to a normalized map wherein
71  // both axes span the 0-1 range only. Thus, this width needs to be
72  // comprised between 0 and 1, wherein 0 = no interpolation (not
73  // recommended) and 1 = everything is interpolated (then the map
74  // loses meaning). A generic value of 0.1 would serve a good
75  // starting guess.
76  interpolationWidth value;
77 
78  // This specifies how the transfer coefficients are interpolated
79  // in the interpolation regions described above. The only possile
80  // modes are linear or quadratic.
81  interpolationMode linear; //quadratic;
82 
83  // Dictionary that holds pairs of point names and point coordinates
84  // (par1_X, par2_X) for a generic point pX in the parameters space.
85  // These points are used to construct the regime domains in the
86  // regime map. The names of the points can be set to anything, as
87  // long as they are referenced correctly in the reigmes dictionary
88  // when building the regime domains
89  regimePoints
90  {
91  p0 (par1_0, par2_0)
92  p1 (par1_1, par2_1)
93  //...
94  pN (par1_N, par2_N)
95  }
96 
97  // Dictionary of all regime domains and the points that define
98  // their boundaries. For any domain, the point list can start
99  // from any point as long as the resulting domain boundaries
100  // (i.e. the lines that connect one point to the next one, and
101  // last back to the first) never cross each other. Both convex
102  // and concave shapes are possible. Please note, however, that no
103  // consistency checks are made to enforce the no-crossing
104  // condition (it will be implemented some time in the future).
105  // The last condition for this approach to work is with regards
106  // to scenarios like the one show below, wherein the boundary
107  // of a domain (AB of ABEF) intersects the straight boundary (CE)
108  // of another domain (EDC) at a given point (B).
109  /*
110  ^ parameter2
111  |
112  |
113  | C
114  | |\
115  | | \
116  | A----------B \
117  | | | \
118  | | | \
119  | | | \
120  | F----------E------D
121  |
122  i-------------------------------------------------> parameter1
123  *//*
124  // In this scenario, while the domain EDC could be constructed
125  // from only those three points (as CE is straight), the code
126  // requires it to be constructed as EDCB (or DCBE, CBED, EBCD, you
127  // get the idea), as if the B point is not included, the "internal
128  // boundary" BE between the two domains will never be recognized
129  // as such, thus leading to outright interpolation errors.
130  regimes
131  {
132  "regime0" (p0 p1 ... pI);
133  "regime1" (p7 p9 ... pJ);
134  //...
135  "regimeM" (p10 p27 ... pK);
136 
137  }
138  }
139  }
140  \endverbatim
